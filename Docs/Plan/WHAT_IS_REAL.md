# What's real vs. not — PS4 platform

A plain-language summary of what actually works vs. what's missing or limited, for anyone (team, judges, Q&A prep) who wants the honest picture without reading the full build log in `PS4_BUILD_STATUS.md`. Update this file whenever a "not real" item becomes real, or a new limitation is found — don't let it go stale.

## Real (built, wired to actual data, verified live)

- Login/auth — real sessions, real password hashing, no public sign-up
- Case creation — real DB rows, FIR/CCTNS number required
- Evidence upload — real SHA-256 computed server-side on the actual stored bytes
- Metadata/EXIF extraction — real (ffprobe / exifr / pdf-parse)
- Image/video deepfake detection — real ML model (`not-lain/deepfake`), real Grad-CAM heatmap
- Audio deepfake/voice-spoofing detection — real ML model (`Gustking/wav2vec2-large-xlsr-deepfake-audio-classification`)
- Face detection box + crop — real MTCNN output (actual detected coordinates + the actual aligned face crop the classifier scored)
- C2PA provenance check — real check (most files simply won't have a manifest — shown as neutral, not suspicious, when absent)
- Perceptual-hash cross-case/corpus matching — real Hamming-distance matching against other cases and the seeded corpus
- Evidence Fusion — real deterministic coverage-capping algorithm, not a mock verdict field
- Human override — real, persisted to the database and the audit trail
- Chain-of-custody audit log — real, hash-chained, cross-checked against an append-only checkpoint file outside the database
- PDF/JSON report export — real, server-rendered, bilingual Section 63 BSA two-part evidentiary certificate
- Role-based access control — real (admin vs. investigator gating, enforced on every route)
- NCII/minor-sensitivity blur-then-reveal — real, the reveal action itself is logged
- Document/PDF metadata extraction + tamper heuristic — real
- Dashboard KPIs — computed from real case/evidence/verdict data, not hardcoded
- Reverse-image search — real multi-provider architecture (one working engine today, Google Cloud Vision Web Detection; structured so a second provider can be added later without a rewrite once real credentials + a confirmed, privacy-safe API contract exist for one). Sends evidence bytes directly to the provider (not a public URL), returns real exact/partial matches, referencing pages, and content labels, each tagged with which provider(s) actually found it; results from every configured provider are merged/deduped by URL into one list. Cached per-provider and re-runnable, credentialed in this environment (`GOOGLE_APPLICATION_CREDENTIALS`). Blocked entirely (403, server-enforced) for NCII/minor-sensitivity evidence — never sent externally. This is real reverse-image search against providers' own indexes, not live scraping of specific social platforms (Telegram/X/WhatsApp) — that distinction still holds, see below.
- AI news-summary cards — for any reverse-image-search matched page, a real fetch of that page's actual public content plus a real Vertex AI Gemini call that judges for itself whether it's genuinely a news article and, if so, produces a real summary (headline/outlet/date/summary) from the real fetched text. Never fabricates a summary for a non-news page or one it couldn't read — falls back to a plain link. Cached by URL (a matched page can recur across evidence items, no reason to re-fetch/re-summarize).
- AI image description — real Vertex AI Gemini call describing an image/video frame and naming any recognizable person as a best-effort lead (never a verified identification); same caching/re-run pattern and same NCII/minor block as reverse-image search above.
- Geographic sighting map (on the propagation page) — real EXIF GPS extraction (when the camera embedded it — most files won't have it, honestly shown as absent) with real offline IP geolocation (`geoip-lite`, bundled city-level database, no live calls, no account/key) as a fallback when a request happened to carry a resolvable public IP. Each point is labeled with its actual source (EXIF GPS vs. IP geolocation) — never blended, never guessed. IP capture itself only works when something in front of the app sets `x-forwarded-for`/`x-real-ip`; running locally with no reverse proxy (e.g. at the venue) means most sightings will have no IP to geolocate, and EXIF GPS will be the source that actually populates points, when present.
- Threat detection (from a call/video transcript) — real Vertex AI Gemini judgment of whether the actual conversation content contains a genuine threat, never inferred from keywords, honestly returns "no threat" for ordinary conversation. Same NCII/minor sensitivity gate as reverse-image search/image description. Cached per-transcript, re-runnable.
- Per-frame Grad-CAM heatmaps (video) — every sampled frame already gets a real heatmap computed by the classifier; all of them are now persisted and browsable (not just the single worst-scoring frame), so the "where in the clip" question has a real answer across the whole video, not one static frame.
- Video diff against a matched original — real frame extraction + pixel comparison (`sharp` + `pixelmatch`) between an exhibit and a real cross-case match's actual file, at the same timestamp the primary heatmap already flags as most suspicious. Only runs when a real file exists to diff against — the seeded corpus only stores a thumbnail, so corpus-only matches get an honest "no full original available" message, never a fake diff. Best-effort visual diff (no frame-registration correction), disclosed as such in the UI.
- PDF digital-signature detection — real, structural: detects a signature via the standard `/ByteRange`+`/Contents` pattern, extracts the signer's name from the embedded certificate, and checks whether the signed byte range still covers the whole current file (the real, well-known way to detect bytes appended after signing). Deliberately does not attempt full PKCS#7 cryptographic verification against a certificate authority trust chain — see the limitation below.
- AI document summary + threat detection — a real Gemini plain-language summary of a document exhibit's actual extracted text, and the same real threat judgment already used for call/video transcripts applied to that text. Same NCII/minor gate, cached per exhibit, re-runnable. Document Details panel also now shows the document's real Producer/Creator tool and SHA-256 (already-extracted fields that weren't previously surfaced).
- Splice-point detection (audio/video) — real short-time spectral-flux analysis (`ml-service/splice_detector.py`, plain numpy FFT, no new dependency) flags timestamps where a clip's frequency content jumps abruptly relative to its own local neighborhood — the automated, cached counterpart to the live waveform/spectrogram visualizer, which only ever showed a human something to look at, computing and storing nothing. A real, checkable heuristic, not a trained splice classifier: ordinary speech sounds (sharp consonants, a cough) also trigger it, so it's presented as a lead to investigate by ear, never proof of editing. Threshold (4.0 standard deviations above local baseline) was tuned against real test data, not picked arbitrarily — verified to catch genuine synthetic splices with wide margin while cutting false positives from ordinary conversational speech.
- Claim verification (on a call/video transcript) — real, live Google Search-grounded Gemini call (`@google/genai`, not the older `@google-cloud/vertexai` client used elsewhere — that SDK only exposes a deprecated search-grounding tool incompatible with the Gemini 2.x models this app uses, confirmed live, not assumed) that searches real, current sources for whether the transcript's actual content was really said/happened, and reports a `confirmed`/`debunked`/`unclear` verdict with real citation links to what it actually found — genuinely different from every other AI feature here, which judges from the model's own training knowledge rather than a live search. Same NCII/minor gate, cached per transcript. Verified live on the platform's own Dwivedi deepfake demo clip: correctly found no real coverage of the specific fabricated quote, and separately caught that the claim even misattributes the real film's director — a genuine, checkable finding from real search, not invented.
- Multi-engine web search (per exhibit) — real search across 3 engines using this exhibit's own extracted text (transcript/document text/AI description) as the query, always investigator-editable: Google (via the same Gemini grounding as claim verification, official), Brave, and DuckDuckGo (real results from their public HTML search pages — no API key/account for either, verified live before wiring in, but unofficial and could break if either changes their markup). Real merge/dedup by URL with per-result attribution (`foundBy`). Each result's domain is also resolved to an approximate server location (DNS → the same offline `geoip-lite` database already used for evidence-sighting IP geolocation) and plotted on a map — disclosed as approximate/often-CDN-skewed, not the publisher's actual location. Same NCII/minor gate as every other external-call route.
- CCTV object/vehicle/plate/face reference matching (PS4 use case #1) — real Faster R-CNN (torchvision, COCO-pretrained) human/vehicle detection on sampled CCTV video frames, real EasyOCR plate reads (region-cropped first, returns nothing rather than a guessed string below a disclosed confidence floor), real cosine-similarity face matching against an investigator-uploaded reference photo (reusing the same 512-d MTCNN embeddings the deepfake pipeline already computes), and real Levenshtein fuzzy plate matching (handles common OCR misreads — O/0, I/1, B/8 — as honest near-matches instead of requiring exact equality). All persisted (`CctvFrameSample`, `VideoObjectDetection`, `CctvFrameFace`, `ReferenceMatchResult`), browsable via `CctvSearchPanel`.
- Cross-evidence relationship mind map + case summary (PS4 use case #6) — real Vertex AI Gemini structured-JSON synthesis across a case's aggregated real text (transcripts/translations, AI image descriptions, per-face labels, document summaries) into an entity/relationship graph plus a narrative summary. Deliberately never extracts from anything the investigator can't already see elsewhere in the app — no fresh OCR/NER pass of its own. Persisted per case (`CaseMindMap`), viewable at `/cases/:id/mindmap`.
- Document integrity verdict (PS4 use case #5, partial) — a real fused verdict for PDF evidence (`fuseDocumentEvidence`, computed automatically at upload) built from the two structural signals that already existed but previously fed no verdict: the PDF digital-signature check and the creation-vs-modification-date tamper heuristic. Correctly never claims `AI_GENERATED` (no document classifier exists) and never claims more than these two checks can honestly support — see the known limitation below for what's still missing.
- General AI-image classifier (`dima806/ai_vs_real_image_detection`, second signal) — a real second, independent full-synthesis detector running alongside the original face-swap classifier on every image/video-frame call. Fusion takes `max()` of the two scores, still governed by the same "zero corroboration → INCONCLUSIVE" cap. First real use of the `AI_GENERATED` verdict (previously unreachable with only one detector). See `ml-service/README.md` → "General AI-image model" for the real tested numbers — a 3-image smoke test confirming direction, not a calibrated accuracy claim.
- Modern-diffusion AI-image classifier (`Organika/sdxl-detector`, third signal) — a real third, independent detector (Swin Transformer, a different architecture family from both models above) targeting SDXL-era diffusion output specifically, added because `dima806`'s own model card admits ~2-year-old training data and "significant concept drift" since. Fusion now takes `max()` of all three scores; whichever of the two general-family models fires is named explicitly in the stored `AI_GENERATED` explanation text, not left anonymous. Stored as `DetectionResult.sdxlProbability` and shown as its own row in the investigation page's signal panel. **License note:** CC-BY-NC-3.0 (non-commercial) — the one model in this service not Apache-2.0/MIT. See `ml-service/README.md` → "Modern-diffusion (SDXL) AI-image model" for the real tested numbers — a 2-image smoke test confirming direction, not a calibrated accuracy claim.

## Not real / not built

The UI says so plainly wherever these would appear — never faked, never a silent gap.

- Live social-platform spread scraping (Telegram/X/WhatsApp propagation tracing) — not built, explicit non-goal; reverse-image search (above) covers "does this appear elsewhere on the web," not "how did it spread across specific platforms"
- "Same person, different photo" matching, general case — still not built as a standalone "search all case/corpus evidence for this face" feature; only exact/near-duplicate *file* matching exists there (hash-based). Gemini image description can name a recognizable person as a best-effort lead, a different (non-biometric) mechanism. The one place real face-embedding matching *does* now exist is narrower and purpose-built: CCTV reference-face matching (above) — an investigator-uploaded reference photo matched by cosine similarity against faces detected in a specific CCTV video's sampled frames, not a cross-case/corpus-wide search.
- Propagation graph — not live social-media scraping; built from a small seeded demo corpus, labeled "illustrative demo corpus" everywhere it's shown
- Anything requiring live internet access at runtime — the whole app is designed to run fully offline after initial setup

## Real, but with a known limitation (disclosed, not hidden)

- **Image classifier**: real model, but calibration testing found it misreads ordinary compressed real-world photos (scores some unedited photos suspiciously high on raw score) and is effectively blind to fully-synthetic (non-face-swap) AI images. The Evidence Fusion engine's corroboration requirement is what protects the final verdict from this — a raw high score with zero corroborating signal is always capped to `INCONCLUSIVE`, never forced to `MANIPULATED`/`AI_GENERATED`. A second, general AI-image classifier (`dima806/ai_vs_real_image_detection`) now runs alongside the original face-swap one specifically to close that full-synthesis blind spot, and its score is what makes the `AI_GENERATED` verdict (vs. `MANIPULATED`) real rather than an unreachable enum value — see `ml-service/README.md` → "General AI-image model" and "Calibration finding" for both models' real tested numbers, including where the new model does and doesn't help. That second model's own limitation (~2-year-old training data, self-disclosed "concept drift") is in turn what a third model (`Organika/sdxl-detector`, see the entry above) exists to close — this is a real, disclosed chain of "model X's own admitted gap is why model Y was added," not three redundant detectors.
- **Video detection has no dedicated model or benchmark**: video reuses the same three image classifiers per sampled frame — there is no temporal/frame-consistency model. A real calibration test (two independently-sourced, provenance-checked clips: a genuine CC-licensed interview vs. an official academic face-reenactment demo) found the fusion output currently cannot separate them — both scored ~100% raw and landed on `INCONCLUSIVE` at the same capped confidence, for different reasons underneath (real per-model signal exists — e.g. SDXL correctly scored the real clip 0.22% — but is masked because fusion takes the max across models/frames). Frame sampling was fixed to scale with clip duration (was a flat 6 frames regardless of length; now ~1 frame per 3s, capped at 20) after this testing showed long videos were badly under-sampled — verified live (60s video: 6→20 frames, +9.4s total latency, still demo-acceptable). A frame-to-frame face-embedding consistency check was attempted as a second signal but explicitly not shipped: real testing found it isn't just under-calibrated, it has a structural gap — the code has no face-tracking across frames, so on any video with more than one visible person it can silently compare two different people's faces. A follow-up idea — treating "2 of 3 classifiers agree" as a corroborating signal — was implemented, tested live, and reverted the same session after it produced a false firm `MANIPULATED` verdict (86% confidence) on the known-real calibration video: the three classifiers turned out to share a correlated blind spot on this content, so their agreement wasn't independent corroboration, it was the same weakness counted three times. Full numbers and both reverted attempts: `ml-service/README.md` → "Video path — real calibration finding and what changed."
- **Audio detector**: only catches voice synthesis/spoofing, says nothing about whether audio was cut or spliced.
- **`chattr +a` audit-log hardening**: doesn't actually work on this filesystem (checked, not assumed) — falls back to mirroring the checkpoint file via syslog instead. Disclosed in code and docs, not silently swapped.
- **Document tamper check**: one narrow, checkable fact (file modified after its stated creation date), not a real forgery-detection model — deliberately does *not* feed into the verdict, since there's no real classifier behind it.
- **PDF digital-signature check**: real structural detection (signature present, signer name, whether the signed range covers the whole file) but deliberately does *not* cryptographically verify the signature (RSA-verify the digest against the certificate's public key, or validate a certificate-authority trust chain) — hand-rolling that correctly against every real signing tool's ASN.1 encoding choices was judged too fragile to ship; a wrong "cryptographically valid" claim would be worse than not making it. The document integrity verdict (above) inherits this same limitation — it's a verdict over structural signals, not cryptographic proof.
- **CCTV plate/face reference matching**: real detection and matching, but the plate OCR is English-only text recognition (not a plate-specialized localizer model) and the face match threshold is a disclosed, reasonable-but-not-scientifically-validated number, not a biometric decision boundary tuned against a large labeled dataset.
- **Video diff**: a best-effort visual pixel diff, not a frame-registration-corrected forensic technique — highlighted pixels show where two frames differ, not necessarily the manipulated region specifically. Only available against real cross-case matches, never the seeded corpus.
- **Web search (Brave/DuckDuckGo)**: real results via each engine's public HTML search page, not an official API (neither project has published one this app has access to) — could stop working if either changes their page markup. Domain-server geolocation is approximate and often reflects a CDN edge location, not the publisher's true physical base.

## One thing worth knowing

A handful of pre-existing curated demo cases (referenced from `Docs/incidents/`, e.g. `CHD-2026-00124`) still render through an old mock-data-driven page that predates this real build — that one *does* show fabricated data on purpose, since it was never migrated. Any case created through the actual app goes through the fully real path and never touches that mock data.
